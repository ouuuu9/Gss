> 代码基准：`backend/`（Spring Boot 3.2.5）、`frontend/`（Vue 3 + Vite 5）、`sql/gss.sql`

## 1. 项目概述

### 1.1 背景与目标

传统集装箱码头闸口作业依赖纸质单证与人工核对，存在信息流转慢、车辆无序排队、费用漏收、操作不可追溯等问题。本系统以"闸口无纸化作业"为目标，模拟集装箱码头从单证录入到审单结算的完整业务闭环，验证以下能力：

1. 单证全生命周期管理（录入、派单、预约、进闸、出闸、审单、作废）；
2. 进港预约与时段容量控制，削峰填谷、避免闸口拥堵；
3. 按业务类型自动计费与缴费放行控制，防止漏收；
4. 多角色数据隔离与操作审计，满足可追溯要求；
5. 作业数据实时可视化（首页看板 + 数据大屏）。

### 1.2 业务名词

| 名词 | 说明 |
|---|---|
| EIR | Equipment Interchange Receipt，集装箱设备交接单，本系统以 EIR 单证为核心载体 |
| PI-F | 提重：提走重箱 |
| PI-E | 提空：提走空箱 |
| GR-E | 还空：归还空箱 |
| GR-F | 还重：归还重箱 |
| 派单 | 运输公司为单证指定执行作业的司机与拖车 |
| 进港预约 | 车辆按日期与时段预约进港，系统限制每时段名额 |
| 进闸 / 出闸 | 车辆通过闸口刷卡（IC 卡）办单，状态推进 |
| 审单 | 码头管理员对已出闸单证做最终审核，业务完成 |

### 1.3 业务流程

```
┌──────────┐   ┌──────────┐   ┌──────────┐   ┌─────────┐   ┌──────────┐   ┌──────┐
│ 单证录入  │──▶│   派单    │──▶│ 进港预约  │──▶│  进闸    │──▶│   出闸    │──▶│ 审单  │
│ CREATED  │   │DISPATCHED│   │APPOINTED │   │ GATE_IN │   │ GATE_OUT │   │ DONE │
└──────────┘   └────┬─────┘   └────┬─────┘   └─────────┘   └────┬─────┘   └──────┘
                    │              │                              │
                    │ 取消派单      │ 取消预约 / 超时自动释放        │ 未缴清费用拦截
                    ▼              ▼                              ▼
                CREATED       DISPATCHED                      禁止出闸
```

关键业务规则：

1. **状态不可越级**：所有写操作先经状态机校验，非法流转直接拒绝；
2. **派单归属校验**：司机、拖车必须属于单证作业公司；
3. **预约名额控制**：每日期每时段默认 10 个名额，原子扣减防超约；
4. **计费规则**：GR-F 还重 50 元/单、PI-F 提重 80 元/单（配置文件可调），派单时生成收费记录；
5. **放行规则**：进闸需存在有效预约；出闸需费用已缴清；
6. **资源回收**：预约超时未进闸由定时任务自动释放名额并回退单证状态。

### 3.3 分层职责

| 层 | 职责 | 禁止事项 |
|---|---|---|
| Controller | 接收参数、`@Valid` 校验、`@RequireRole` 角色声明、组装 `Result` | 不写业务判断、不直接访问 Mapper |
| Service | 状态机校验、归属校验、计费、事务边界、CAS 调用 | 不感知 HTTP、不返回 `Result` |
| Mapper | SQL 与结果映射 | 不写业务逻辑 |
| Entity / DTO / VO | 数据库映射 / 入参 / 出参 | 不混用职责 |

### 3.4 关键选型说明

**为什么不用 Spring Security 过滤链？**  
本系统权限模型简单（4 角色、无动态权限），使用 `HandlerInterceptor` + 自定义 `@RequireRole` 即可完整覆盖认证与授权，代码量小、链路透明，便于教学与答辩讲解。密码加密仍复用官方 `spring-security-crypto` 的 BCrypt，不重复造轮子。

**为什么不用 Redis？**  
数据规模与并发量均在单机可承受范围。幂等、会话状态均放在 JVM 内即可满足毕设场景；文档中已明确该方案的局限（仅单实例有效）及生产化改造方向。

**为什么选择状态机而不是大量 if-else？**  
规则集中、可测试、防越级、易扩展。详见 5.2。

## 5. 核心模块设计

### 5.1 认证与授权

**登录流程**：

```
LoginDTO → AuthService.login
  1. 按用户名查 sys_user
  2. BCrypt.matches 校验密码
  3. 校验 status = 1
  4. 组装 LoginUser → JwtUtil 签发 token
  5. 返回 { token, user }
```

**JWT 载荷**：

```
sub            : userId
username/name  : 用户名与姓名
role           : 角色
companyId      : 公司（数据权限）
driverId       : 司机（数据权限）
iat / exp      : 签发与过期时间（默认 12 小时）
算法            : HS256
```

**请求鉴权链**：

```
请求 → JwtInterceptor.preHandle
  1. 放行非 Controller 方法
  2. 校验 Authorization: Bearer <token>
  3. 解析 JWT（伪造/过期 → 401）
  3.1 按 userId 回查用户状态（禁用/删除的账号，已发出的 token 立即失效 → 401）
  4. 读取方法/类上的 @RequireRole，角色不匹配 → 403
     （先于 UserContext.set：preHandle 返回 false 时本拦截器的
       afterCompletion 不会被调用，避免 ThreadLocal 残留）
  5. UserContext.set(loginUser)（ThreadLocal）
  6. afterCompletion 清理 ThreadLocal
```

**数据权限三层防护**：

| 层 | 手段 |
|---|---|
| 查询参数 | Controller 根据角色覆写 `companyId` / `driverId` |
| 单条操作 | Service 中 `checkCompanyOwnership` / driverId 比对 |
| 数据返回 | VO 查询 SQL 已带过滤条件，无法通过改 ID 越权 |

> WebSocket 握手同样校验 token，且仅 ADMIN / GATE 可连接大屏（`/ws/screen?token=`）。

### 5.2 状态机

**实现**：`EirStateMachine` 维护 `Map<当前状态, Map<事件, 目标状态>>`，全部不可变（`Collections.unmodifiableMap`）。

| 当前状态 | 事件 | 目标状态 |
|---|---|---|
| CREATED | DISPATCH | DISPATCHED |
| CREATED | CANCEL | CANCELLED |
| DISPATCHED | CANCEL_DISPATCH | CREATED |
| DISPATCHED | APPOINT | APPOINTED |
| DISPATCHED | CANCEL | CANCELLED |
| APPOINTED | CANCEL_APPOINT | DISPATCHED |
| APPOINTED | EXPIRE_APPOINT | DISPATCHED |
| APPOINTED | GATE_IN | GATE_IN |
| APPOINTED | CANCEL | CANCELLED |
| GATE_IN | GATE_OUT | GATE_OUT |
| GATE_OUT | AUDIT | DONE |
| DONE / CANCELLED | 任意 | 拒绝 |

**接口**：

```java
String validateAndTransition(String currentStatus, String event); // 非法抛 BusinessException
boolean canCancel(String currentStatus);                          // CREATED/DISPATCHED/APPOINTED
```

**设计收益**：

1. 规则集中在一张表，新增事件只改一处；
2. 所有写操作强制过状态机，杜绝越级（如未预约直接进闸）；
3. 纯 POJO 无外部依赖，单元测试成本极低；
4. 错误提示统一为"当前状态【X】不允许执行操作：Y"，便于前端直接展示。

**测试覆盖**（`EirStateMachineTest`，40+ 用例）：

- 11 条合法转移；
- 14 条非法转移；
- DONE / CANCELLED 终态；
- 未知状态与 null 状态；
- 完整业务链路与回退链路。

### 5.3 派单与计费

**单条派单**（`EirService.dispatch`）：

```
1. 单证存在性校验
2. 公司归属校验（COMPANY 只能派本公司单证）
3. 状态机：CREATED + DISPATCH → DISPATCHED
4. 司机、拖车存在、为启用状态（status=1）且同属单证作业公司
5. CAS 更新状态与派单信息
6. 生成收费记录：
   GR-F → 50 元（gss.fee.amount）
   PI-F → 80 元（gss.fee.pickup-amount）
   其余类型不收费
```

**取消派单**：`DISPATCHED → CREATED`，清空司机/拖车；若收费记录已缴费则拒绝取消（避免钱已收但记录消失、账实不符），未缴费则删除该单证已生成的收费记录，保证费用与业务状态一致。

**批量派单**：多张单证派给同一司机与拖车。

```java
@Lazy @Autowired private EirService self;  // 自注入代理

for (Long id : ids) {
    try { self.dispatch(id, single, operator); }
    catch (BusinessException e) { failures.add(eirNo + "：" + e.getMessage()); }
}
```

自注入的意义：直接 `this.dispatch()` 不经过 Spring 代理，`@Transactional` 失效；通过 `self` 调用可让**每条派单拥有独立事务**，单条失败不影响整批。

### 5.4 预约与容量控制

**创建预约**（`AppointmentService.create`）：

```
1. 单证存在、未作废
2. 状态机：DISPATCHED + APPOINT → APPOINTED
3. 时段合法性：必须属于 8 个标准时段
4. 日期合法性：不早于今天；当天时段已过则拒绝
5. 身份校验：
   DRIVER  → 只能预约派给自己的单证
   COMPANY → 只能预约本公司单证，司机必须是派单司机
6. 车牌：未传则按派单拖车带出
7. 容量控制：
   INSERT IGNORE 初始化容量记录
   UPDATE ... SET booked_count = booked_count + 1
          WHERE ... AND booked_count < capacity
   影响行数为 0 → 该时段已约满
8. 插入预约记录
9. CAS：单证 DISPATCHED → APPOINTED
```

**原子性说明**：容量扣减是**单条条件 UPDATE**，校验与扣减在同一语句内完成，由 InnoDB 行锁保证并发串行，从根本上避免"先查后改"的超约问题。

**取消预约**：`APPOINTED → DISPATCHED`，预约置 CANCELLED，归还名额（`GREATEST(booked_count-1, 0)`），全部带 CAS 条件防重复释放。

**时段配置**：`06:00-22:00` 共 8 个两小时时段；单时段默认容量 10（`Constants.DEFAULT_SLOT_CAPACITY`）。

### 5.5 闸口办单

**进闸**（`GateService.checkin`）：

```
IC 卡 → 拖车（不存在/停用 → 拒绝）
  → 找该拖车最早一张 APPOINTED 单证（无 → 拒绝）
  → 校验存在 ACTIVE 预约（无 → 拒绝）
  → CAS 推进 GATE_IN，记录 gate_in_time
```

**出闸**（`GateService.checkout`）：

```
IC 卡 → 拖车
  → 找该拖车 GATE_IN 单证（无 → 拒绝）
  → 校验收费记录已缴清（有记录且未缴 → 拒绝）
  → CAS 推进 GATE_OUT，记录 gate_out_time
```

**审单**（`GateService.audit`）：ADMIN 执行，`GATE_OUT → DONE`，记录 `audit_time`。

**拦截提示**均为具体原因（"没有已预约待进闸的单证""尚有未缴清费用"），便于闸口人员定位问题。

### 5.6 收费与报表

| 功能 | 实现要点 |
|---|---|
| 单笔缴费 | 校验记录存在、归属本公司、未缴；`UPDATE ... WHERE pay_status = 0` 防重复 |
| 批量缴费 | 过滤出"本公司 + 未缴"记录后批量置为已缴，返回实际笔数 |
| 收费报表 | 按公司聚合：总笔数、已缴笔数、未缴笔数、已缴金额、总金额 |
| 数据权限 | COMPANY 仅能查询/缴纳本公司费用 |

### 5.7 AOP 横切设计

| 注解 | 切面 | 时机 | 说明 |
|---|---|---|---|
| `@Idempotent(ttlSeconds=3)` | IdempotentAspect（Order=1） | Around | 指纹 = 用户ID + 方法签名 + 参数 MD5，窗口内重复请求返回"请勿重复提交" |
| `@RefreshScreen` | ScreenRefreshAspect（Order=2） | AfterReturning | 写操作成功后广播大屏 |
| `@AuditLog("描述")` | AuditLogAspect | Around | 成功/失败均落库，参数递归脱敏（password → ***），审计失败不影响业务 |

执行顺序保证：幂等最先（重复请求不产生审计日志、不触发大屏刷新），刷新其次，审计环绕全程。

**局限说明**：幂等指纹存于 JVM `ConcurrentHashMap`，仅适用于单实例；集群部署需改为 Redis 分布式去重。

### 5.8 定时任务

| 任务 | 周期 | 逻辑 |
|---|---|---|
| 预约超时释放 | 60s | 扫描过期 ACTIVE 预约 → CAS 置 EXPIRED → 归还名额 → 单证 APPOINTED 回退 DISPATCHED |
| 大屏心跳推送 | 30s | 向全部在线大屏广播最新统计，兼作连接保活 |

超时判定（SQL）：

```sql
status = 'ACTIVE'
AND (appt_date < CURDATE()
     OR (appt_date = CURDATE()
         AND SUBSTRING_INDEX(time_slot, '-', -1) < DATE_FORMAT(NOW(), '%H:%i')))
```

逐条 try-catch，单条异常不阻塞整批；全部 CAS，避免与用户取消/进闸并发重复释放。

### 5.9 数据大屏（WebSocket）

| 项 | 说明 |
|---|---|
| 端点 | `/ws/screen?token=<JWT>` |
| 鉴权 | 握手阶段解析 token，仅 ADMIN / GATE 允许连接 |
| 推送时机 | 连接建立推全量；`@RefreshScreen` 写操作后；30s 心跳 |
| 并发安全 | 会话存 `ConcurrentHashMap`；发送时 `synchronized(session)`，失败会话剔除 |
| 数据内容 | 今日进/出闸、实收/应收金额、7 状态分布、4 业务类型分布、近 7 日趋势 |

### 5.10 Excel 导出

`ExcelExporter`（Apache POI）统一生成 `.xlsx`：单证、预约、收费三处导出复用查询逻辑并继承同样的数据权限过滤，导出不会绕过权限。

### 5.11 数据完整性与软删除

数据库未建 FOREIGN KEY 约束，完整性由应用层兜底：

**1. 删除保护（物理删除前校验）**

| 删除对象 | 校验 |
|---|---|
| 运输公司 | 逐一检查司机、拖车、单证、收费记录、系统用户 5 张表，存在关联即拒绝删除 |
| 司机 / 拖车 | 存在进行中单证（已派单/已预约/已进闸）→ 拒绝删除 |

**2. 软删除混合策略（司机 / 拖车）**

| 场景 | 行为 |
|---|---|
| 有进行中单证 | 拒绝删除 |
| 仅有历史单证（DONE / CANCELLED） | 软删除：`status=0` 置为停用，历史单证列表仍能正常 JOIN 出司机姓名、车牌号 |
| 无任何单证引用 | 物理删除，保持表干净 |

已停用的司机/拖车：派单接口校验 `status=1` 直接拒绝；派单/绑定下拉列表前后端均过滤；司机档案下拉的 `listAll` 后端过滤。EIR 单证本身无删除入口，天然永久保留。

**3. 写入归属与存在性校验**

- 司机创建/修改：绑定拖车必须存在且属于同一运输公司；`companyId` 必须真实存在；
- 拖车创建/修改：`companyId` 必须真实存在；
- 单证创建/修改：`validateBusiness` 校验 `companyId` 存在性（create/update 共用入口）；
- 系统用户创建/修改：非码头端角色 `companyId` 必须存在；DRIVER 角色的 `driverId` 必须存在且司机档案属于所选公司，防止档案错配导致司机登录后看不到自己的预约。

## 8. 并发与一致性设计

| 场景 | 风险 | 方案 |
|---|---|---|
| 重复点击派单 | 重复生成收费记录 | `@Idempotent` 3s 窗口 + CAS `WHERE status='CREATED'` |
| 两人同时派同一单 | 重复计费 | CAS，影响行数 0 抛冲突 |
| 重复刷 IC 卡 | 状态反复推进 | CAS `WHERE status='APPOINTED'/'GATE_IN'` |
| 并发预约同一时段 | 超卖 | `UPDATE ... WHERE booked_count < capacity` |
| 取消预约与超时任务并发 | 名额重复归还 | `UPDATE ... WHERE status='ACTIVE'` CAS |
| 重复缴费 | 重复扣款 | `UPDATE ... WHERE pay_status=0` |
| 批量派单部分失败 | 整批回滚 | `self` 代理逐条独立事务 |

设计原则：**幂等注解负责用户体验（快速拦截并友好提示），CAS 负责最终一致性（数据库层兜底）**，两者互补。

## 11. 设计亮点

1. **状态机驱动业务**：7 状态 9 事件的转移表集中管理，40+ 单元测试保障，彻底杜绝状态越级。
2. **全链路 CAS 防并发**：状态更新统一携带 `expectedStatus` 条件，覆盖派单、预约、刷卡、缴费、取消、超时释放。
3. **数据库原子防超约**：条件 UPDATE 一条语句完成"校验 + 扣减"，利用 InnoDB 行锁保证并发正确性。
4. **AOP 三件套零侵入**：幂等、审计、大屏刷新全部注解化，业务代码保持纯粹。
5. **后端强制数据权限**：JWT 内嵌身份 + Controller 覆写查询条件 + Service 归属校验，前端无法绕过。
6. **预约资源闭环**：创建扣减、取消归还、超时自动释放，名额始终准确。
7. **WebSocket 实时大屏**：握手鉴权、事件驱动推送、定时兜底、会话并发安全。
8. **批量操作事务隔离**：自注入代理保证逐条独立事务，部分失败不拖垮整批。
9. **审计可追溯**：操作人、IP、参数（已脱敏）、结果、耗时全量落库。
10. **文档化接口**：springdoc 生成 Swagger，便于联调与验收。
11. **数据完整性兜底**：无 FK 约束下应用层保完整——删除前关联校验、有历史改软删除（`status=0`），派单拒绝已停用资源。

| 3 | JWT 密钥、数据库密码写在 yml | 泄露风险 | ✅ 已解决：改为环境变量注入 |
| 4 | CORS 允许任意来源且带凭证 | 跨站风险 | 收敛为白名单域名 |
| 5 | 无接口级限流 | 暴力试探 | 网关或拦截器加限流 |
| 6 | 进闸按"最早一张 APPOINTED"匹配 | 同车多单可能选错 | 按预约日期/时段精确匹配 |
| 7 | 仅状态机有单元测试 | 回归保障不足 | ✅ 已解决：新增 DataPermissionTest + CompanyScopeTest + FeeServiceTest + SoftDeleteTest（共 57 用例） |
| 8 | 大屏 30s 全量查询 | 数据量大时压力上升 | 增量推送或缓存快照 |
| 9 | 审计日志无归档策略 | 长期膨胀 | 按月分区 / 定期归档 |
| 10 | 派单未校验司机/拖车状态 | 停用资源仍可派单 | ✅ 已解决：dispatch 校验 `status=1`，已停用司机/拖车直接拒绝 |

### 13.2 常见问题与回答要点

| 问题 | 回答要点 |
|---|---|
| 为什么用状态机？ | 规则集中、防越级、可单测；对比 if-else 的维护成本 |
| 并发派单会重复收费吗？ | 不会：幂等注解 3s 窗口 + CAS `WHERE status='CREATED'`，影响行数 0 即冲突回滚 |
| 预约名额怎么防超卖？ | 条件 UPDATE 单语句完成校验与扣减，InnoDB 行锁串行化 |
| 为什么不用 Spring Security？ | 权限模型简单，自定义拦截器链路透明；BCrypt 仍用官方组件 |
| 数据权限怎么保证？ | JWT 内嵌 companyId/driverId；Controller 覆写查询参数；Service 二次归属校验 |
| 幂等的局限？ | 内存实现仅单实例，集群需 Redis |
| 批量派单如何保证部分成功？ | 自注入代理走事务，逐条独立提交 |
| 删除有历史单证的司机/拖车会怎样？ | 有进行中单证直接拒绝；仅有历史单证则软删除（status=0 停用），历史数据展示不受影响；无引用才物理删除 |
| 超时预约怎么处理？ | 60s 定时任务扫描，CAS 置 EXPIRED、归还名额、单证回退 |
| 系统有什么不足？ | 见第 12 章，主动说明生产化改造方向 |
