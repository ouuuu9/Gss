> 版本 1.0 · 2026-10-27
> 面向：开发者交接、技术评阅、答辩准备

## 1. 项目概述

### 1.1 是什么

B/S 架构的集装箱码头闸口无纸化作业模拟系统。覆盖从单证录入到审单完成的全链路业务：

```
单证录入 → 派单 → 司机预约 → 刷卡进闸 → 办单放行 → 出闸 → 收费结算 → 审单完成
```

四种角色协作：

| 角色 | 职责 |
|---|---|
| ADMIN（码头管理员） | 录入单证、用户管理、审单、全部报表 |
| GATE（闸口办单员） | 刷 IC 卡进闸/出闸办单 |
| COMPANY（运输公司用户） | 派单、预约、缴费、查看本公司数据 |
| DRIVER（司机） | 创建/取消本人预约、刷卡进闸 |

### 1.2 解决什么问题

传统码头闸口依赖纸质单证和人工核对，高峰期排队严重、状态追踪困难、费用结算滞后。本系统模拟的核心命题：**在有限时段容量下，如何让 4 种角色并发协作且数据不串、状态不乱、费用不丢。**

### 1.3 业务体验路径（推荐演示顺序）

1. admin 登录 → 录入 GR-F 还重单（会产生 50 元收费）
2. company1 登录 → 对单证派单（选本公司司机+拖车）
3. company1 或司机 → 创建预约（选日期时段）
4. company1 → 收费管理 → 批量缴费
5. gate 登录 → 输 IC 卡号 → 进闸办单（无有效预约会被拦）
6. gate → 同一卡号 → 出闸办单（未缴费会被拦）
7. admin → 审单 → 单证 DONE
8. 收费报表 / 首页看板 → 查看统计

## 3. 数据库设计

### 3.1 9 张表一览

| # | 表名 | 职责 | 关键唯一约束 |
|---|---|---|---|
| 1 | transport_company | 运输公司基础档案 | code |
| 2 | sys_user | 系统账号（4 种角色统一在此表） | username |
| 3 | tractor | 拖车档案（IC 卡模拟刷卡） | ic_card_no |
| 4 | driver | 司机档案 | — |
| 5 | eir_order | **核心业务表**，7 状态流转 | eir_no |
| 6 | appointment | 进港预约 | — |
| 7 | fee_record | 收费记录 | — |
| 8 | appt_slot_capacity | 时段容量（并发防超约关键表） | (appt_date, time_slot) |
| 9 | audit_log | AOP 自动记录的操作审计 | — |

全部字段带中文 COMMENT。种子数据含 2 家公司、3 台拖车、3 名司机、2 张示例单证；系统账号由 DataInitializer 首次启动时 BCrypt 加密入库。

### 3.2 关键设计点

**sys_user 单表承载 4 角色**：不拆 4 张表，用 `role` 字段区分；`company_id` 对码头端用户为空，`driver_id` 仅 DRIVER 角色填充。登录时按 role 分支处理数据权限。

**eir_order 状态机字段**：`status` VARCHAR(20) 存 7 种状态字符串而非 TINYINT 枚举，可读性优先。所有时间戳字段（gate_in_time / gate_out_time / dispatch_time / audit_time）按业务节点即时记录。

**appt_slot_capacity 行锁模型**：这是防超约的核心表。`UPDATE appt_slot_capacity SET booked_count = booked_count + 1 WHERE appt_date = ? AND time_slot = ? AND booked_count < capacity`——单条 SQL 原子完成容量扣减，InnoDB 行锁保证并发安全，不需要分布式锁。

### 3.3 索引策略

- 高频查询条件：eir_order(status)、eir_order(company_id)、appointment(appt_date)
- 外键索引：eir_order(tractor_id)、eir_order(driver_id)、driver(company_id)
- 唯一索引覆盖业务约束：uk_eir_no、uk_ic_card_no、uk_date_slot、uk_code

## 4. 认证与权限

### 4.1 JWT 认证链路

```
登录 → AuthService → BCrypt 校验密码 → JwtUtil.createToken(LoginUser{userId, role, companyId, driverId})
                                                    ↓
                                          客户端存 localStorage，后续请求带 Authorization: Bearer <token>
                                                    ↓
                                          JwtInterceptor.preHandle
                                            1. 校验 Bearer 前缀
                                            2. jwtUtil.parseToken → LoginUser
                                            2.1 sysUserMapper.selectById → 回查用户状态
                                                （禁用/删除的账号，已发出的 token 立即失效）
                                            3. UserContext.set(loginUser) — 放入 ThreadLocal
                                            4. @RequireRole 注解校验角色
                                                    ↓
                                          Controller 执行业务
                                                    ↓
                                          afterCompletion → UserContext.clear() — 防止 ThreadLocal 内存泄漏
```

JWT 有效期 12 小时。密钥通过环境变量 `JWT_SECRET` 注入，不入库。

### 4.2 数据权限矩阵（后端强制，不依赖前端）

数据权限在 `CompanyScope` 统一解析，所有 Controller 的列表/详情接口调用 `CompanyScope.of()` 获取生效过滤条件，不直接信任前端传来的 companyId / driverId。

| 角色 | companyId 过滤 | driverId 过滤 | 说明 |
|---|---|---|---|
| ADMIN | 透传参数（可查全体） | 透传参数 | 管理员全权限 |
| GATE | 透传参数 | 透传参数 | 闸口员按卡号操作 |
| COMPANY | **强制本公司**（无视前端传值） | 透传参数 | 防止 company2 看 company1 的数据 |
| DRIVER | null（不限公司） | **强制本人司机** | 司机只能看自己的预约和单证 |

写操作（update/delete）额外在 Service 层加归属校验：`record.companyId == user.companyId`（COMPANY 角色时），否则拒绝。

### 4.3 @RequireRole 角色校验

方法级注解，支持多角色白名单，方法注解优先于类注解：

```java
@RequireRole({"ADMIN", "GATE", "COMPANY"})
@GetMapping
public PageResult<FeeRecordVO> list(...) { ... }
```

DRIVER 被排除在收费查询之外——即便前端菜单隐藏，接口层也会拦。

## 5. 状态机引擎

### 5.1 7 状态 9 事件

状态转移表在 `EirStateMachine` 构造函数中以 `Map<当前状态, Map<事件, 目标状态>>` 形式声明，静态不可变：

```
CREATED ──DISPATCH──▶ DISPATCHED ──APPOINT──▶ APPOINTED ──GATE_IN──▶ GATE_IN ──GATE_OUT──▶ GATE_OUT ──AUDIT──▶ DONE
    │                    │                       │
    └──CANCEL──▶ CANCELLED ←──CANCEL_DISPATCH──┘ ←──CANCEL_APPOINT──┘
                                    EXPIRE_APPOINT ──▶ DISPATCHED（定时任务触发）
                                    
GATE_IN / GATE_OUT / DONE / CANCELLED 为终止态，无出边。
```

**可作废状态**：`CREATED / DISPATCHED / APPOINTED`——车辆一旦进闸（GATE_IN），单证物理上就在场，不允许作废。

### 5.2 调用方式

Service 层每次写操作前先调状态机校验，不合法直接抛 `BusinessException`：

```java
String targetStatus = stateMachine.validateAndTransition(eir.getStatus(), EirEvent.DISPATCH);
// ... 业务逻辑 ...
eirMapper.updateStatus(eirWithExpectedStatus);  // CAS 条件更新
```

### 5.3 与 CAS 的协作

状态机保证**业务上**不能越级跳转（比如从 CREATED 直接进闸），CAS 条件更新保证**并发上**不会乱序（比如两个请求同时读到 DISPATCHED，一个派单、一个进闸）。

CAS 的 SQL 模式：

```sql
UPDATE eir_order SET status = #{newStatus}, ... WHERE id = #{id} AND status = #{expectedStatus}
```

返回受影响行数，0 表示状态已被其他请求改变，抛出冲突异常。

## 6. 并发防护三层

### 6.1 第一层：@Idempotent 幂等切面（Order=1，最先执行）

防止用户连续点击 / 网络重试导致重复派单、重复缴费、重复刷卡。

**指纹算法**：MD5( userId | 方法签名 | 非 ServletRequest 参数 toString 拼接 )

**存储**：ConcurrentHashMap<指纹, 过期时间戳>，TTL 默认 3 秒，超过 1000 条时惰性清理过期条目。

**拦截时机**：在审计日志和大屏刷新之前（Order=1），重复请求不产生审计记录。

### 6.2 第二层：CAS 条件更新

全链路状态变更、预约状态变更、容量归还全部走 `WHERE status = 前置状态` 的条件更新。在 InnoDB 行锁下，只有一个事务能成功，其余事务受影响行数为 0，立即回滚。

CAS 还用于：
- **作废单证时归还预约名额**：`appointmentMapper.updateStatusIf(id, CANCELLED, ACTIVE)`，防止作废与取消预约并发时重复释放
- **定时任务释放过期预约**：同样走 CAS，防止定时任务与用户主动取消 / 进闸操作冲突

### 6.3 第三层：时段容量原子扣减

防超约的最后一道防线。单条 SQL 完成检查 + 扣减：

```sql
UPDATE appt_slot_capacity 
SET booked_count = booked_count + 1 
WHERE appt_date = ? AND time_slot = ? AND booked_count < capacity
```

受影响行数 = 0 即已满，应用层提示"该时段约满"。这比先 SELECT 再 UPDATE 的做法安全得多——InnoDB 行锁在这条 SQL 执行期间锁住该时段行，其他并发请求排队。

## 7. AOP 三件套

三个切面按 Order 顺序执行：

| Order | 注解 | 切面 | 作用 |
|---|---|---|---|
| 1 | @Idempotent | IdempotentAspect | 防重复提交，入口即拦截 |
| 2 | @AuditLog | AuditLogAspect | 记录谁/何时/IP/操作/参数/耗时/结果，参数自动脱敏（BCrypt 密码不记录） |
| 3 | @RefreshScreen | ScreenRefreshAspect | 方法成功执行后，通过 WebSocket 向大屏推送刷新通知 |

### 7.1 @AuditLog 脱敏策略

切面在记录请求参数前，递归遍历参数对象，识别并替换以下字段：
- password / pwd / token → `******`
- 身份证号 → 保留前 6 后 4 位

### 7.2 @RefreshScreen 触发大屏刷新

大屏（Screen.vue）通过 WebSocket 订阅 `/topic/screen`。当派单 / 进闸 / 出闸 / 缴费等关键业务方法执行成功后，切面发送一条简单刷新指令，前端收到后自动重新拉取统计数据——不需要轮询。

## 8. 收费与预约

### 8.1 收费规则（application.yml 可配）

| 业务类型 | 收费 | 说明 |
|---|---|---|
| GR-F 还重单 | 50 元/单 | 派单时自动生成 fee_record |
| PI-F 提重单 | 80 元/单 | 同上 |
| PI-E 提空 / GR-E 还空 | 0 元 | 不生成收费记录 |

**取消派单时**：若已缴费则拒绝取消（提示先退费）；若未缴费则物理删除 fee_record，保证账实一致。

**出闸前强制缴清**：GateService.gateOut 校验 eir 关联的所有 fee_record.pay_status，未全部为 1 则拦截。

### 8.2 预约容量模型

```
appt_slot_capacity 表：
  appt_date (2026-10-27) + time_slot (08:00-10:00) → 唯一键
  capacity = 10（默认，可调）
  booked_count = 3（已占用）
```

时段配置：每天 8 个两小时时段（08:00–22:00），首次创建预约时自动初始化对应日期 + 8 个时段的 capacity 记录。

### 8.3 定时释放

ApptReleaseTask 每 60 秒扫描：
1. 找出所有 status=ACTIVE 且时段已过的 appointment
2. CAS 置为 EXPIRED（防止与用户取消 / 进闸并发）
3. 归还 booked_count（slotCapacityMapper.release）
4. 若关联 eir 仍为 APPOINTED，CAS 回退为 DISPATCHED

单条异常不阻塞整批——每条 try/catch，日志记录后继续下一条。

### 11.4 排查清单

| 现象 | 可能原因 | 排查 |
|---|---|---|
| 前端请求 500 + ECONNREFUSED | 后端没起来 | `netstat -ano \| findstr :8080` 看有无监听 |
| 后端启动报 Access denied | DB_PASSWORD 未设或错 | 设环境变量后重启 |
| 登录报"账号已被禁用或删除" | JwtInterceptor 回查触发 | 查 sys_user.status 是否为 0 |
| 超时段预约成功但约不上 | booked_count 未释放 | 查 appt_slot_capacity.booked_count 是否与预约表对不上 |
| 审计日志为空 | 方法没加 @AuditLog | 加注解；切面 Order=2 在幂等之后 |
| 大屏不刷新 | WebSocket 未连上 | 浏览器 Console 看 WebSocket 连接状态 |
